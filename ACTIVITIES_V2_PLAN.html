Summary

Lesson activities v1 is committed in a1d0cad and partly deployed, with no production data (owner, 2026-10-21). V2 therefore replaces v1 shapes outright: no compatibility with v1 payloads, runs or cached rows is needed. The catalogue grows from seven types to nine.

  • Remove quick_grammar everywhere. Add guided_grammar (ordered steps over lesson blocks, each with a choice question), read_aloud and speak_from_english.
  • Story summary gains sentence pairs with hover linking, the section image, and a display-only word dictionary.
  • Answering a guided grammar step advances lesson reading progress. This reverses the v1 “never change progress” rule (D4).
  • Every activity carries 1–3 metrics. The completion screen shows only the metrics that changed (D5) and an “Up next” list (D6).
  • The lesson’s “Do more with AI” area gets a completed-count badge, grows upward, and shows one icon per type (D7).

The plan has 24 task cards in six batches (0–5). Every task is its own commit on main, which also marks the task done in this file.

Owner decisions D1–D7

Decided 2026-10-21. These are product rules. Tasks implement them; no task may change them.

D1 · Story summary

  • The recap shows Dutch sentences and their English translations. Hovering or focusing a Dutch sentence highlights its English pair, and the reverse.
  • The section’s image (the first image block in the section, including inside columns) appears at the top of the summary activity when present.
  • A left-side word dictionary lists new words used in this section that the lesson does not already teach. It reuses the visual UI of the lesson’s new-words panel (LessonWords). Display only: no bookmarking, no word memory changes.
  • The lesson’s own word list (collectLessonWords terms) goes to the model as “already taught”. The model decides which other words from the section to return in newWords. Validation is shape-only (strict contract). The server only dedupes case-insensitively within the list and against the lesson’s terms.
  • On completion, suggest “understand grammar”: the next section’s grammar activity, if a next grammar section exists.

D2 · Speaking: two new, separate activity types

  • read_aloud: the learner reads each Dutch line aloud, with pronunciation feedback. Model-free: the lines come from the published lesson.
  • speak_from_english: the learner sees English and produces the Dutch line. English translations are model-written by position (same contract style as role-play cues). The Dutch reference stays server-derived.
  • Source: story sections (the sections that today get story_summary). Lines are their dialogue turns (speaker kept) plus prose text split into sentences (speaker null), at most 60 lines.
  • “Hint and self-navigating from English” is future work and out of scope. Role-play stays unchanged; merging it is a future decision.

D3 · Guided grammar

  • The new type guided_grammar replaces quick_grammar, which is removed everywhere. grammar_explanation and tricky_grammar stay as they are.
  • Generated once and cached and shared like every activity. No live per-learner adaptation.
  • The model receives the grammar section’s blocks as a numbered list of chunks and returns ordered steps. Each step has 1–4 chunk indices (prefer atomic: one sub-rule or one example group per step) and one small choice question (3 options, correctIndex, explanation) that checks or continues teaching that chunk. 2–12 steps in total.
  • Chunks ascend in document order across steps, should cover the section, and never overlap.
  • The model never writes IDs. The server maps chunk indices to lesson block IDs and snapshots those blocks (immutable, stored in the payload).
  • UI: one slide per step. Top: a step progress bar. Below it: the step’s lesson blocks, rendered with the read-only lesson renderer (LessonBlocks). Under that: the small question with feedback. Once the answer is checked, Continue appears.
  • The model also returns followUps: 0–2 suggestions from the enum [tricky_grammar, mixed_practice, grammar_explanation] (for example, tricky mixing negation and questions with the new topic). The server keeps only the types actually eligible in this lesson.
  • The completion screen offers “Back to the lesson’s practices”: a link to the first practice block inside the source section (hash = block id), otherwise the normal return link.

D4 · Progress (reverses the v1 rule)

v1 rule being replaced: “Required lesson completion, required practice progress … never change through activities.”

Why it was forbidden: the owner asked. It was only a v1 scoping default (LESSON_ACTIVITIES_PLAN.html:146), added to avoid out-of-scope memory and fluency effects. It was not a principle.

  • New rule: answering a guided_grammar step marks the lesson blocks shown in that step as read for lesson progress. The implementation uses the existing reading-position model: advance the viewer’s saved lesson position to the step key of the last shown block only if it is further than the current saved position (never move backwards), then run the existing completeIfWhole.
  • Note for the docs: reading share is “furthest position”, so this also credits earlier steps, the same as a reader scrolling ahead. This is a decision the owner can revisit. The alternative is a per-block read set, which is a bigger change.
  • Archived courses and unsaved runs: no progress write.
  • Word memory never changes through activities.

D5 · Gamified progress on completion (all types)

  • Each generated activity payload carries metrics: 1–3 keys chosen by the model from an enum. The model never sees numbers. read_aloud (model-free) uses the fixed default [lesson_share].
  • Metric enum. Values are 0–1 and computed server-side for the viewer:
KeyMeaning
lesson_sharelessonShare of this lesson (“% of Lesson 8 done”)
lesson_readingReading half of the lesson share
lesson_grammarShare of this lesson’s grammar sources whose guided_grammar run is completed at the current fingerprint
lesson_activitiesShare of this lesson’s suggested activities completed at current fingerprints
  • When a run starts (the first open that creates the run, and on restart), the server snapshots all metric values into the run (metrics_before JSON). On completion, the response includes before and after for the activity’s requested keys.
  • The UI shows only metrics that changed, as progress bars with friendly copy, for example “+6% of this lesson’s grammar” and “Lesson 8 is now 42% done (+2%)”. If none changed, the block is hidden.

D6 · Completion screen “Up next” (all types)

In this order: the model’s followUps (guided_grammar only), then the next source’s suggestions in document order (the next section’s activities), then Back to lesson (existing), then Back to practices (guided_grammar only).

D7 · “Do more with AI” area on the lesson page

  • The header gets a badge with the count of this lesson’s completed activities, taken from the existing completed list.
  • The area expands upward (taller), and the new-words panel shrinks vertically to make room.
  • Every activity type gets its own unique icon. The icons come from lucide-react (^1.52); each export must be verified in node_modules before use. Proposed mapping:

Out of scope

  • Hint and self-navigation for speaking from English (future work, D2).
  • Merging role-play into the new speaking types.
  • Vocabulary and word-memory effects of any activity.
  • Live adaptive generation per learner.
  • A per-block read set for progress (the furthest-position rule in D4 stays).

Execution protocol

  • Roles. The orchestrator is the main session (Opus). Workers are Haiku 5.5 subagents, one task each, with a fresh context.
  • Prompt. Each worker prompt is the task card verbatim, plus the read rule below. Use the template in the box.
  • Read rule. Workers read only the files listed under Read. They search only when a listed symbol has moved. They never read docs other than those listed, never read todo.md, and never run full suites.
  • Report. Maximum 10 lines: DONE or BLOCKED, files changed, commands run with pass/fail counts, one-line deviations. No diffs and no pasted logs.
  • Review. The orchestrator reviews rtk git diff --stat and spot-checks files. It reads full diffs only for tasks marked ⚠ or when a check fails.
  • Retry. A failing task gets ONE retry with the error excerpt (20 lines at most). A second failure escalates to a Sonnet worker or the orchestrator.
  • Parallelism. Tasks marked parallel-safe touch disjoint files and may run at the same time. Everything else runs in sequence.
  • Commits (owner rule, revision 4). One commit per task on main (the owner works alone on main), made by the orchestrator right after the task’s Verify passes. Subject: activities v2 T1.2: <card title>. The same commit updates this file: the card’s Status field becomes Done YYYY-MM-DD — <checks run, pass counts> and one row is added to the Status log. Hashes are not written into this file (a commit cannot contain its own hash); find a task’s commit with rtk git log --grep "T1.2". A BLOCKED task is not committed; its Status becomes Blocked — <reason> and is committed with the next task. The commit message ends with the Co-Authored-By line above.
  • Risk. Tasks marked ⚠ get a full-diff review by the orchestrator.
